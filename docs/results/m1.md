# M1 test results

Recorded 2026-10-05 on the author's machine (Intel Core i7-13700H, 20 logical cores, Windows 11):
OpenJDK 21.0.12 with Maven 3.9.11 and JUnit 6.1.3; Python 3.14.5 (GIL build) with pytest 9.1 and
mypy; Node.js 24.19.0 with TypeScript 7.0.2. CI re-runs everything on Ubuntu (Temurin 21, Python
3.12, Node.js 24), plus the Python suite on the free-threaded 3.14t build with the GIL disabled.

## Tests: 101 passed, 0 failed

Command: `make test`. Every suite reads `spec/scenarios.json` (4 producers x 2,000 items through a
4-slot buffer; 200 tasks on 4 workers; 2,000 items through a 3-stage pipeline failing at item
1,234; 64 concurrent cache misses; 5 philosophers x 200 meals with a 300 ms timeout).

| Problem | Java (27) | Python (40) | JavaScript (34) |
|---|---|---|---|
| Bounded buffer | 7: exactly once, FIFO per producer, fills to capacity and never past it, close, blocking put, abort wakes waiters, timeouts, interrupt | 8: the same on threads and on asyncio | 5 on the event loop, plus 5 for `SharedRingBuffer` and `SharedMutex` with real threads |
| Worker pool | 4: every result, `maxActive == workers`, failure isolated, shutdown drains then rejects, submit blocks when full | 6: threads and asyncio | 6: `worker_threads`, tasks proved to run on several OS threads |
| Pipeline | 6: ordered equals sequential, unordered, failure names stage and item with no worker left, early stop on a 200,000-item input, backpressure | 9: threads and `asyncio.TaskGroup` | 6 |
| Single-flight cache | 5: 64 callers share one load, keys load in parallel (rendezvous), failure not cached, LRU eviction, nulls rejected | 7: threads and asyncio | 5 |
| Dining philosophers | 5: naive deadlock forced and detected; ordered and seats cannot form the cycle and eat all 1,000 meals; 10 rounds of free contention | 10: threads and asyncio | 7, plus mutex and barrier |

Lint: `make lint` is clean (javac `-Xlint:all -Werror`; `ruff check`, `ruff format --check` and
`mypy --strict` on 22 files; `tsc --checkJs --strict`). Audit: `pip-audit` and `npm audit` found no
known vulnerabilities.

### Flakiness check

Each suite was run repeatedly after the final change: Java 5 times, Python 3 times, JavaScript 3
times in full and the shared-memory file 8 more times. All runs passed. Two problems found on the
way are recorded here because they are the kind of bug this repo is about:

- A JavaScript test waited for a worker's `exit` event by attaching the listener after receiving
  the worker's result. A fast worker could exit first, so the test sometimes hung for 60 seconds.
  Fixed by attaching the listener when the worker is created.
- A first version of the early-stop check asserted that at most "items in flight" finish after a
  failure. Abort is asynchronous, so on a busy machine up to 160 more items finished before every
  buffer was aborted. The check now uses a 200,000-item input and asserts only that far fewer than
  half are processed.

### Mutation check

Seven deliberate bugs were applied one at a time (then reverted); each was caught:

| Mutation | Result |
|---|---|
| Java: single-flight disabled, every caller loads | 2 of 27 tests fail |
| Java: ordered strategy takes the left fork first | 2 of 27 fail (the forced cycle forms) |
| Java: pipeline does not abort on failure | 1 of 27 fails (the early-stop test) |
| Python: buffer capacity check off by one (`>` instead of `>=`) | a pool test hangs and `pytest-timeout` stops the run |
| Python: ordered strategy takes the left fork first | 3 of 40 fail |
| JavaScript: `SharedMutex` never actually locks | 1 of 34 fails (non-atomic increments are lost) |
| JavaScript: failed cache flights are never cleared | 2 of 34 fail |

(Two earlier mutations survived a first version of the suite, Java pipeline without abort and the
ring buffer without its mutex. The early-stop and `SharedMutex` tests were added because of them.)

## Scheduling experiments (`make scheduling`)

Single runs on the machine above. They show the models, not benchmark results (M3); CPU-bound
ratios vary between runs (Java showed 4.5x and 14x on two runs, Python 0.5x and 0.9x).

| Experiment | Wall time | OS threads used |
|---|---|---|
| Java: 10,000 tasks sleeping 100 ms, one virtual thread each | 181 ms | 20 |
| Java: 1,000 tasks sleeping 100 ms, pool of 50 platform threads | 2,229 ms | 50 |
| Java: 20 CPU-bound tasks on virtual threads vs the same work on 1 thread | 555 ms vs 7,780 ms (14.0x) | 20 |
| Python 3.14 (GIL): 10,000 asyncio tasks sleeping 100 ms | 186 ms | 1 |
| Python 3.14 (GIL): 1,000 tasks sleeping 100 ms, pool of 50 threads | 2,017 ms | 50 |
| Python 3.14 (GIL): 4 CPU-bound tasks on 4 threads vs one after another | 534 ms vs 505 ms (0.9x) | 4 |
| Node.js 24: 10,000 promises sleeping 100 ms on the event loop | 111 ms | 1 |
| Node.js 24: 4 CPU-bound tasks on 4 worker threads vs one after another | 813 ms vs 2,847 ms (3.5x) | 4 |

What they show: 10,000 blocked virtual threads cost about as much as 10,000 asyncio tasks or
promises, while running on only 20 OS threads; a fixed pool of platform threads is limited by its
size (1,000 / 50 x 100 ms = 2 s). For CPU-bound work, Java and Node.js worker threads run in
parallel, but CPython threads with the GIL do not (no speedup, sometimes a slowdown from lock
handoffs). CI prints the same table for the free-threaded 3.14t build in its job summary.
